## [2026-09-26] - Daily Log - Hardening Cloud Armor du sample `alb-internal`

Durcissement de la policy Cloud Armor régionale de `samples/alb-internal`, à partir d'une revue de `infra/armor.tf`. Toutes les affirmations ci-dessous ont été vérifiées sur source primaire (schéma du provider Terraform épinglé + documentation Google) avant implémentation.

- **armor.tf — parsing JSON** : ajout d'`advanced_options_config { json_parsing = "STANDARD" }`. Au défaut GCP (`DISABLED`), Cloud Armor évaluait le corps de requête comme une **chaîne plate uniforme** : faux positifs sur les caractères structurels du JSON, et contournements SQLi encodés en JSON. L'API n'expose pourtant que du JSON (`POST /api/items`, `@RequestBody`). `request_body_inspection_size` volontairement non déclaré : le défaut est déjà 64 kB, soit le maximum configurable.
- **armor.tf — rulesets CRS 3.3 → CRS 4.22** : migration de `-v33-stable` vers `-v422-stable`. Motif décisif : **CRS 3.3 n'inclut pas le ruleset `java`** (« Not included » dans la doc Google), le plus pertinent pour cette stack Spring Boot 4 / Java 25 (désérialisation CVE-2015-4852, Struts CVE-2017-9805, Log4Shell 944150).
- **armor.tf — sensibilité explicite** : passage d'`evaluatePreconfiguredExpr()` à `evaluatePreconfiguredWaf(..., {'sensitivity': 1})`. Le premier hérite du défaut implicite **sensibilité 4** (paranoia level 4 OWASP, toutes signatures), très bruyant. Vérifié avant application que **chaque ruleset retenu possède au moins une signature de niveau 1**, donc qu'aucun n'est silencieusement vidé par ce réglage.
- **armor.tf — couverture OWASP** : 2 rulesets (SQLi, XSS) → 8. Ajout de `rce`, `java`, `protocolattack`, `methodenforcement`, `cve-canary` (appliqués) et `scannerdetection` (en `preview`, sa signature unique ciblant les user-agents de scanners et les tests e2e utilisant `curl`). Écartés comme hors modèle de menace : `lfi`/`rfi` (aucun service de fichiers), `php`/`nodejs` (stack Java), `sessionfixation` (pas de session, IAP en amont), `json-sqli-canary` (couverture largement recouverte par la signature 942550, déjà incluse au niveau 1 dans `sqli-v422-stable` ; la variante canary est un peu plus large — vecteurs SQLi dans l'URL — mais ne justifie pas une règle facturée de plus).
- **armor.tf — `throttle` → `rate_based_ban`** : un simple `throttle` laissait l'attaquant sonder **indéfiniment** à exactement 100 req/min, soit le scénario d'énumération lente depuis une VM compromise. Ban de 10 min au-delà de 600 req/5 min — calibré pour laisser passer 5 exécutions consécutives de `task e2e-cyber` (~120 requêtes chacune). `conform_action = allow` conservé : cette règle reste l'allow de `subnet-isolated`.
- **armor.tf — plan de priorités documenté** : bandes 100–299 (deny explicites), 300–499 (`preview`), 500–899 (appliqué), 900 (rate-limit/allow), 2000 (deny-by-default). Cloud Armor s'arrêtant à la première règle qui matche, toute règle WAF déclarée **au-dessus de 900 serait du code mort** — invariant désormais verrouillé par un test.
- **monitoring.tf (nouveau) — détection** : `log_config` était déjà actif à 100 % sur le backend service (logs produits et facturés) mais jamais exploité. Ajout de 2 métriques log-based — `armor-denied` (règles appliquées) et `armor-preview-matched` (bande `preview`, sans laquelle une règle en preview est inobservable donc inutile) — plus une `google_monitoring_alert_policy` au-delà de 50 blocages/5 min. Label `rule_priority` extrait pour distinguer blocage WAF / rate-limit / source non autorisée. Activation des APIs `logging` et `monitoring` dans `main.tf`.
- **variables.tf** : ajout d'`alert_notification_channels` (liste, vide par défaut, avec `validation {}` sur le format `projects/<p>/notificationChannels/<id>`).
- **scripts/e2e-cyber.sh** : le test ne couvrait que la **query string** — il passait au vert sans rien dire de la surface JSON en écriture. Ajout d'un `check_post()` et d'un test SQLi dans le corps JSON d'un `POST`, la surface que `json_parsing = STANDARD` rend précisément inspectable. Sections renumérotées 1/3, 2/3, 3/3.
- **Tests** : `terraform test` passe de **6/6 à 10/10**. Les nouveaux blocs verrouillent l'invariant de priorités, l'usage d'`evaluatePreconfiguredWaf` + sensibilité 1, la présence du ruleset `java`, le maintien de `scannerdetection` en preview, `rate_based_ban` + `conform_action = allow`, et les métriques de détection. **Vérifié par injection de régression** : passer une règle WAF à la priorité 950 fait bien échouer le test dédié (un test qui ne peut pas échouer ne vaut rien).
- **Non retenu à ce stade** : `log_level = "VERBOSE"` sur la policy. Sans lui, les logs indiquent « bloqué par la règle 500 » **sans l'ID de signature**, ce qui rend impossible la construction des `preconfigured_waf_config { exclusion { target_rule_ids } }` nécessaires au tuning des faux positifs.
- **Écarté après vérification** : Adaptive Protection, Google Threat Intelligence, bot management/reCAPTCHA, géographie et ASN client, Address Groups, Security Command Center — **non supportés** sur une policy régionale attachée à un ALB interne (matrice officielle + absence d'`adaptive_protection_config` dans le schéma du provider). Documenté dans le README pour éviter de les rechercher.

Les rulesets `*-canary` en miroir des `*-stable` (reco Google) n'ont **pas** été dupliqués pour cette raison ; la bande 300–499 est documentée et utilisée pour le seul ruleset au risque de faux positif non vérifiable hors-ligne.
